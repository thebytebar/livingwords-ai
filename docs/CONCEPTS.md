# Architecture and concepts

LivingWords is local desktop AI with trusted, private skills for serious users: a private AI for writing, thinking, planning, and software tasks, built around a pretrained Gemma model:

- **Model:** Gemma 4 E2B Instruct provides language ability; the project does not pretrain or fine-tune model weights.
- **Inference:** Electron desktop builds run the model through a bundled `llama.cpp` runtime on macOS, Windows, and Linux.
- **Interfaces:** the desktop app is the supported product; there is no CLI or HTTP web interface.
- **Skills:** general-purpose chat with a Christian persona informed by historic Trinitarian Christianity and the Bible, plus user-created task skills, attached local documents, an in-app browser, and an approval-gated terminal tool. Each skill has a short description and a free-text prompt describing when to activate and how to complete the task; `@tool_name` tokens expose only matching registered tool functions while that skill runs. A local model evaluates whether a skill matches a request, then asks before running an inferred match. Explicit slash-command selections run directly and include the selected skill description and prompt in context. Legacy workflow definitions in workflows.json are migrated by combining their activation guidance, ordered steps, and goal into the prompt, with the description initialized from the prompt's first sentence. Skill prompts do not grant tool permissions or bypass validation and approval requirements. User-created skills are stored in skills.json; existing workflows.json data is migrated without deleting the original file. The Christian perspective is used when relevant to faith, theology, and ethics, not forced into unrelated answers. The desktop agent can retrieve, search, and read only documents attached to the active conversation. It can propose text-file edits only after an explicit user request and cannot write them without approval. Terminal commands run only after the user approves the exact command.
- **Conversation context:** the Electron app stores chat sessions locally and supplies the conversation history when generating follow-up answers. Older messages are compacted into a bounded summary when needed to fit the configured model context; recent messages remain verbatim as space allows.
- **Local documents:** The Documents panel can reference code, configuration, and other text files or text-based PDFs and folders in place. The agent starts with attached-reference metadata, then uses tool calls shown in the chat's activity cards to scan folders, search, and read files. Folder inspection prioritizes README files, manifests, entry points, architecture notes, tests, and representative source; broad reviews should describe meaningful coverage limits. Retrieved passages are cited, and document text is treated as untrusted data. If explicitly asked to change an attached text file, the agent can propose a replacement; the app displays a diff and writes nothing unless the user approves. PDFs are read-only; the user can open attached files in the viewer. Deleting a conversation removes references and derived indexes, never the originals. Scanned PDFs and OCR are not supported.
- **Web research:** Searches navigate directly to DuckDuckGo's HTML search page with a GET request, while the Web Search tab displays DuckDuckGo's own page without normal browser navigation controls. Clicking links opens separate Browser tabs. DuckDuckGo is the only currently available provider in the provider dropdown; no API key is required. Every page opened by the assistant gets its own Browser tab, where it can read bounded page text and links. Opening pages in the background preserves the user's current panel selection. Users can also navigate to a search site themselves and ask the assistant to read that page. At the start of each request, the assistant reviews open Browser and Web Search tabs and may close those it determines are no longer relevant; tabs needed as context remain open. Web content is untrusted; search queries go to DuckDuckGo and page requests go to external services. If DuckDuckGo requests human verification, complete the challenge in the Web Search tab; rate limits are reported without being bypassed. Browser contexts are isolated per conversation and are not persisted across app restarts.
- **Built-in tools:** arithmetic uses a bounded deterministic expression parser; local date/time comes from the device. Terminal commands are single-line and only execute after the user approves the exact command through the existing confirmation flow.
- **Explicit tool selection:** the chat composer offers the Tools-page catalog through `@` mentions. Selected tool names travel separately from the user's question and instruct the agent to call those exact tools when available; context-specific availability and existing permission and approval safeguards remain in force.
- **Privacy:** inference runs locally on the device, and conversation data is stored locally. Web search and browsing send requests to external websites. The Electron renderer cannot access Node.js or the filesystem directly; web pages run in a separate sandboxed browser view without Node.js access.
- **Cost model:** there is no account, subscription, or per-prompt cloud fee. Users provide the hardware, storage, and power needed to run the model.

The desktop client bundles its pinned GGUF model into each Electron build. `npm install` downloads and verifies the model into the ignored project model cache before the build injects it into app resources. The installed app does not download weights on first launch. See the [desktop build guide](DESKTOP.md) for artifact pins and release caveats.

## Memory profile

The desktop Settings window offers 8K, 16K, 32K, 64K, and 128K context windows, with 16K as the default. Use a larger window only for long threads or large attached folders. Final answers use the configured response cap, up to 3,000 tokens (2,000 with the 8K window); tool turns remain capped at 1,500 tokens. Turn limits are separate rather than a cumulative request-wide budget. Larger contexts use more memory; changing the context restarts the local inference runtime and cancels any active response.

## Scope and local data

Chat prompts are processed by the bundled local model. Conversation history, document references, extracted text, and indexes stay in the app's local user-data directory; they are not sent to a cloud service. Only files and folders explicitly attached to the active conversation are available to the agent. Each run starts with bounded relevant excerpts and folder guidance; the agent can search, read, and navigate those attached sources on demand. Source citations link to the local document viewer, and the Documents panel records which excerpts were included in context. Retrieved text, project guidance, and remote web pages are untrusted data. Web search queries go to DuckDuckGo's HTML search endpoint, and page requests go to external websites. No search API key is stored. Browser contexts are isolated per conversation and held in memory for the app session. Terminal commands require approval of the exact command, and text-file edits require an explicit user request and approval of the displayed diff; PDFs are read-only. Folder indexing is recursive; bulk indexing skips hidden entries, symlinks, `.gitignore` matches, and common generated/dependency folders. Individual files are limited to 20 MB, and derived text plus search indexes share a 250 MB cache budget across conversations. Scanned-PDF OCR is not supported. External knowledge collections and automatic cross-conversation memory are not included. Existing `.livingwords/index.json` and desktop `index.json` files are ignored and left untouched. The selected context window and its corresponding response limit apply to each request.

The model is pretrained and is not fine-tuned by this project. It can make mistakes; verify answers when accuracy matters.

## Agent harness core

`src/core/agent-loop.ts` provides a reusable, typed agent control loop. `createAgentHarness({ model, tools, ...options }).run(task)` returns a `RunResult` with a final answer, stop reason, metrics, and a versioned JSON-serializable `Trace`. Every model turn appends one `Step` with the model's optional concise rationale, requested calls, tool observations, token usage, elapsed time, guardrail decisions, and deterministic verification outcomes. A tool can provide `final_answer_on_success` to finish a run with a deterministic completion message after the tool succeeds, without an unnecessary extra model turn. Traces also retain content-free context assembly, model, and tool timings; estimated input size and its character-based method; and queue-wait/skill-routing timings when supplied by the host. Prompt text, tool arguments, retrieved content, and summaries are not included in these performance fields. Tools are validated and permission-checked as a batch before any call in that batch executes; `ask`-tier tools pause with `needs_human` unless an approval callback explicitly allows them.

The loop supports single-response completion and repeated tool/model turns, bounded steps and context, abort-signal force stops, optional per-tool and final verifiers, and progressive tool disclosure. With `tool_discovery` enabled, the model starts with a compact capability catalog and `tool_get_details`; it requests schemas for named tools before those tools become callable on a later turn. Discovery is limited to registered and allowed tools, and discovered tools still pass through the same input validation, permission checks, execution guards, and tracing as directly exposed tools. Successful tool calls are fingerprinted by tool name and canonical arguments; a duplicate is rejected with one correction attempt, and a repeated duplicate stops the run. Progress events identify the active step before the model responds; chat activity cards show a text-free **Thinking...** card during deliberation, then a **Decision** card with the model's reasoning once recorded. Cancellation also stops waiting on operations that have not yet honored the abort signal. Set `require_verification` to require every executed tool to have a verifier; configure `stop_on_verification_failure` to choose whether a failed tool verification immediately halts the run. `src/core/context-engine.ts` contains the default per-run assembly and compaction policy. When a host supplies the model window and output reserve, budgeting includes the system prompt and currently exposed tool schemas as well as serialized context, with an additional safety margin; actual prompt usage from the local runtime calibrates later per-run estimates, while estimates remain explicitly labeled. Older step details are summarized into a bounded context summary while a configurable window of structured recent steps is retained. A model adapter must return an explicit `done` signal and a final answer when complete. Run `npm run demo:agent-loop` for a local multi-step example that verifies changes against in-memory environment state and prints the full structured trace.

Desktop chat runs through the same harness using a local chat-completions adapter. Conversation history stays structured; attached-reference metadata is passed separately while document content is fetched only through tool calls; tokens from tool-using model turns are withheld, and only the validated final-answer turn is published to the user; each run's versioned trace is published live and saved with its assistant response. The desktop enables progressive tool disclosure: it gives the model a concise catalog, then exposes only the requested tool schemas after `tool_get_details` returns them. Explicitly selected tools are available immediately. Every assistant turn retains its own activity history in the chat. The current activity is shown while the assistant works; completed cards are grouped in a collapsed disclosure, with each tool's function name and a plain-language explanation of its use and outcome. The assistant's response remains in the conversation and is not duplicated as an activity card. Activity hides internal permission and verification checks, errors, and context updates. Web searches describe the query, and reading a specific web-page URL opens it in the Browser tab before reading its content. The assistant can close unneeded Browser and Web Search tabs through a scoped right-panel tool; closing a Browser tab also releases its browser view, while other tab types cannot be closed by the assistant. The right panel contains tool and file tabs; it does not open when a request starts, but may open automatically when the assistant creates a panel tab. A manually opened panel is not restored when switching chats or reopening the app. The harness exposes API web search plus page open/read tools, search/read/folder-navigation tools scoped to attached references, an explicit edit-proposal tool, a visible Browser tab for page navigation, deterministic calculator and local date-time tools, and a terminal command tool routed through the approval dialog. Desktop routing uses deterministic high-confidence rules for clear request modes; an uncertain mode can trigger a bounded, tool-free intent-and-confidence classification call to the same local Gemma runtime. A low-confidence, invalid, or failed mode classification continues through the standard agent flow. This classification only chooses a request mode and does not change tool permissions, validation, or approval requirements. User-created skill definitions are validated and stored in the local user-data directory; a local routing turn filters candidates before a bounded, confidence-checked skill-selection call to the local model, skipping that extra request when no candidate has meaningful keyword overlap. The selected skill's full prompt becomes task guidance. An inferred match is proposed and requires an affirmative user response before the skill runs; a slash-command selection is explicit and runs directly. Skill prompts are guidance rather than formal proof of factual correctness. Conversation storage validates traces and caps each at 1 MB and 20 steps, remaining compatible with earlier sessions that have no trace field. Writing a document always requires approval of the review dialog.
