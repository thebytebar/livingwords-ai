# Architecture and concepts

LivingWords is local desktop AI with trusted, private workflows for serious users: a private AI for writing, thinking, planning, and software tasks, built around a pretrained Gemma model:

- **Model:** Gemma 4 E2B Instruct provides language ability; the project does not pretrain or fine-tune model weights.
- **Inference:** Electron desktop builds run the model through a bundled `llama.cpp` runtime on macOS, Windows, and Linux.
- **Interfaces:** the desktop app is the supported product; there is no CLI or HTTP web interface.
- **Workflows:** general-purpose chat with a Christian persona informed by historic Trinitarian Christianity and the Bible, plus user-created task workflows, attached local documents, an in-app browser, and an approval-gated terminal tool. Workflow definitions describe when they should activate, ordered steps, and a goal; a local model selects one only when the request is a clear match. User-created workflows are stored locally. Workflows guide the agent but do not grant tools or bypass permissions. The Christian perspective is used when relevant to faith, theology, and ethics, not forced into unrelated answers. The desktop agent can retrieve, search, and read only documents attached to the active conversation. It can propose text-file edits only after an explicit user request and cannot write them without approval. Terminal commands run only after the user approves the exact command.
- **Conversation context:** the Electron app stores chat sessions locally and supplies a bounded history from the selected conversation when generating follow-up answers.
- **Local documents:** The Documents panel can reference code, configuration, and other text files or text-based PDFs and folders in place. The agent starts with attached-reference metadata, then uses Activity-visible tool calls to scan folders, search, and read files. Folder inspection prioritizes README files, manifests, entry points, architecture notes, tests, and representative source; broad reviews should describe meaningful coverage limits. Retrieved passages are cited, and document text is treated as untrusted data. If explicitly asked to change an attached text file, the agent can propose a replacement; the app displays a diff and writes nothing unless the user approves. PDFs are read-only; the user can open attached files in the viewer. Deleting a conversation removes references and derived indexes, never the originals. Scanned PDFs and OCR are not supported.
- **Web research:** The assistant searches DuckDuckGo Lite at `lite.duckduckgo.com` and displays results in a dedicated Web Search tab with DuckDuckGo attribution. DuckDuckGo is the only currently available provider in the provider dropdown; no API key is required. Every page opened by the assistant gets its own Browser tab, where it can read bounded page text and links. Opening pages in the background preserves the user's current panel selection. Users can also navigate to a search site themselves and ask the assistant to read that page. Web content is untrusted; search queries go to DuckDuckGo and page requests go to external services. If DuckDuckGo requests human verification, LivingWords reports it and does not bypass the challenge. Browser contexts are isolated per conversation and are not persisted across app restarts.
- **Built-in tools:** arithmetic uses a bounded deterministic expression parser; local date/time comes from the device. Terminal commands are single-line and only execute after the user approves the exact command through the existing confirmation flow.
- **Privacy:** inference runs locally on the device, and conversation data is stored locally. Web search and browsing send requests to external websites. The Electron renderer cannot access Node.js or the filesystem directly; web pages run in a separate sandboxed browser view without Node.js access.
- **Cost model:** there is no account, subscription, or per-prompt cloud fee. Users provide the hardware, storage, and power needed to run the model.

The desktop client bundles its pinned GGUF model into each Electron build. `npm install` downloads and verifies the model into the ignored project model cache before the build injects it into app resources. The installed app does not download weights on first launch. See the [desktop build guide](DESKTOP.md) for artifact pins and release caveats.

## Memory profile

The desktop Settings window offers 8K, 16K, 32K, 64K, and 128K context windows, with 32K as the default. The response limit is approximately one quarter of the selected window, rounded down to the nearest 1,000 tokens and capped at 10,000. Larger contexts use more memory; changing the context restarts the local inference runtime and cancels any active response.

## Scope and local data

Chat prompts are processed by the bundled local model. Conversation history, document references, extracted text, and indexes stay in the app's local user-data directory; they are not sent to a cloud service. Only files and folders explicitly attached to the active conversation are available to the agent. Each run starts with bounded relevant excerpts and folder guidance; the agent can search, read, and navigate those attached sources on demand. Source citations link to the local document viewer, and the Documents panel records which excerpts were included in context. Retrieved text, project guidance, and remote web pages are untrusted data. Web search queries go to DuckDuckGo Lite, and page requests go to external websites. No search API key is stored. Browser contexts are isolated per conversation and held in memory for the app session. Terminal commands require approval of the exact command, and text-file edits require an explicit user request and approval of the displayed diff; PDFs are read-only. Folder indexing is recursive; bulk indexing skips hidden entries, symlinks, `.gitignore` matches, and common generated/dependency folders. Individual files are limited to 20 MB, and derived text plus search indexes share a 250 MB cache budget across conversations. Scanned-PDF OCR is not supported. External knowledge collections and automatic cross-conversation memory are not included. Existing `.livingwords/index.json` and desktop `index.json` files are ignored and left untouched. The selected context window and its corresponding response limit apply to each request.

The model is pretrained and is not fine-tuned by this project. It can make mistakes; verify answers when accuracy matters.

## Agent harness core

`src/core/agent-loop.ts` provides a reusable, typed agent control loop. `createAgentHarness({ model, tools, ...options }).run(task)` returns a `RunResult` with a final answer, stop reason, metrics, and a versioned JSON-serializable `Trace`. Every model turn appends one `Step` with the model's optional concise rationale, requested calls, tool observations, token usage, elapsed time, guardrail decisions, and deterministic verification outcomes. Tools are validated and permission-checked as a batch before any call in that batch executes; `ask`-tier tools pause with `needs_human` unless an approval callback explicitly allows them.

The loop supports single-response completion and repeated tool/model turns, bounded steps and context, abort-signal force stops, and optional per-tool and final verifiers. Progress events identify the active step before the model responds; the Activity tab shows a text-free **Thinking...** card during deliberation, then a **Decision** card with the model's reasoning once recorded. Cancellation also stops waiting on operations that have not yet honored the abort signal. Set `require_verification` to require every executed tool to have a verifier; configure `stop_on_verification_failure` to choose whether a failed tool verification immediately halts the run. Older step details are summarized into a bounded context summary while a configurable window of structured recent steps is retained. A model adapter must return an explicit `done` signal and a final answer when complete. Run `npm run demo:agent-loop` for a local multi-step example that verifies changes against in-memory environment state and prints the full structured trace.

Desktop chat runs through the same harness using a local chat-completions adapter. Conversation history stays structured; attached-reference metadata is passed separately while document content is fetched only through tool calls; response chunks continue to stream through the existing request queue; and each run's versioned trace is published live to the permanent Activity tab and saved with its assistant response. The Activity panel shows a **Decision** entry before each assistant action and one card per practical user-facing action; the assistant's response remains in the conversation and is not duplicated as an activity card. Waiting cards show only a progress title; completed cards show only their title until expanded, with plain-text details and no labeled tool metadata. It hides internal permission and verification checks, errors, and context updates. Web searches describe the query, and reading a specific web-page URL opens it in the Browser tab before reading its content. Assistant activity preserves the user's selected right-panel tab; if the panel is closed, it opens on Activity. The harness exposes API web search plus page open/read tools, search/read/folder-navigation tools scoped to attached references, an explicit edit-proposal tool, a visible Browser tab for page navigation, deterministic calculator and local date-time tools, and a terminal command tool routed through the approval dialog. User-created workflow definitions are validated and stored in the local user-data directory; a local routing turn selects a clearly matching workflow, whose steps and goal become task guidance for the agent. Workflow goals are guidance rather than formal proof of factual correctness. Conversation storage validates traces and caps each at 1 MB and 20 steps, remaining compatible with earlier sessions that have no trace field. Writing a document always requires approval of the review dialog.
